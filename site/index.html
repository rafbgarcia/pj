pj JSON benchmarks

pj vs yyjson and simdjson on three CPUs, five kinds of JSON, and documents from 1 KB to 256 MB. Every number is a median over repeated runs in fresh processes, and every parser's traversal checksum must agree.

Method

  • Parsers. yyjson (DOM), simdjson DOM, simdjson On-Demand, pj on one thread (pj-1t) and pj on all cores (pj). Same compiler and flags for all (-O3 -march/-mcpu=native), library commits pinned. simdjson picks its best kernel at runtime.
  • Process isolation. Each (parser, file, round) runs in a fresh process. There are 3 rounds, each running the parsers in a different random order, and every metric is the median across rounds. The tooltip shows the spread within a run: the interquartile range of the samples.
  • Cold. The first parse in that fresh process, so it includes page faults and first-touch allocation. This is what a one-shot load (a CLI or a request handler's first document) pays.
  • Parse. Steady state, until the document is ready to query. The time budget is 1 s per measurement loop, with at least 5 samples. Each sample is the mean of enough back-to-back documents to last at least 200 µs, so timer overhead stays below 0.1%. For simdjson On-Demand, parsing is lazy (the work happens when values are read), so compare it on end-to-end.
  • End-to-end. Parse, then visit every value (numbers summed, string and key bytes counted), then free. This is the whole cost of using a document once. simdjson reuses its parser buffers, as its documentation recommends, so its free costs nothing. pj reuses its buffers the same way: freed tape mappings and worker contexts (shapes) are cached for the next document.
  • Memory. Peak memory during the cold parse and walk, above the footprint just before it, divided by the input size. The input buffer is excluded; worker threads and their stacks are included. The peak is reset right before the parse: on Linux with /proc/self/clear_refs and VmHWM, on macOS with the footprint interval maximum. Shown for documents of 256 KB and up, because page granularity makes smaller ones meaningless. Linux transparent huge pages are in their default madvise mode. pj requests them only for documents of 16 MB and up, and only where its tape is written densely.
  • CPU. CPU time of all threads (user + system) per document, divided by wall time, which gives the number of cores used. It includes pj's worker threads spinning briefly after each job.
  • Counters. Cycles, instructions and branch misses per input byte for single-threaded parsers. On Linux they come from perf_event on the measuring thread; on macOS from proc_pid_rusage, which gives no branch misses.
  • Pinning and machines. On Linux, single-threaded parsers are pinned to CPU 2. The machines are AWS c8i.4xlarge, c8a.4xlarge and c8g.4xlarge on-demand instances in us-east-1 (Ubuntu 24.04, clang 18). Cloud VMs do not expose frequency control, so the numbers include turbo behavior.
  • Data. Five deterministic families, each filled to a ladder of sizes from repeating element pools, so every machine parses identical bytes. Generator, runner and raw results are in the repository (pj/suite).
